## Method

Measured source revision: `babea92b24a095fdc671e90990fab0d2c949deea` on `nick/human-action-items/spike-projection-cost`. The final code measurement passed in 14.833 seconds including command startup/build checks. `docs/measurements/human-action-items-projection-cost/summary.json` records hashes of the measured harness, approval helper and tracker responder. `github.json.gz` and `linear.json.gz` retain raw requests; decompress with Python gzip or gzip -dc. Later report/capture commits do not change the measured code.

Actual measurement drives the compiled CLI and existing GitHub/Linear plugins over real loopback HTTP, plus the released onevcs write-policy boundary using synthetic public identities. Each workload starts with 2,000 items, has 100 unique tasks and 10 simultaneous managers sharing that tracker. Each task has one terminal resolution: 34 complete, 33 dismiss without reason, 33 dismiss with a reason. Linear uses its existing organization project P-1, not a new project. Public work succeeds; separate private and mixed/private requests to the public GitHub source fail with zero mutations. This proves existing screening/refusal paths, not the future purpose-specific route declaration or project-human API.

**Existing calls measured, not a projection implementation:** GitHub CLI create 850 requests/points, separate required-priority update 200, resolve 300: 1,350 total, 13.5/item. The current CLI cannot set priority at create. Ten cold terminal retries add 10 requests; ten subsequent warm retries add zero. Private/mixed refusal probes add 10 reads separately. Thus 1,370 existing-path requests/points including those probes. The parent-project member reads account for 250 calls as the shared project grows; these are project-scoped pagination, never a whole-board scan. Readback with comments costs another 100 calls.

**Measured warm plugin prototype:** it calls the existing TaskSource.write_task/update_task/query_tasks/check_status_write methods. It carries item_id, owner, state, priority, repositories, parent and a stable origin on the existing Task/ItemWrite shapes. It does not implement project-human, alter producer/consumer declarations, or pretend to implement durable claims. It holds field/repository mappings and preflights the project once per manager. The source invalidates the parent context after addSubIssue, so 90 repeated parent reads remain visible rather than being subtracted arithmetically.

A single cold lifecycle, INCLUDING its own project/field setup, is measured at 8 requests/points and 8 mutation fields; that exact measured increment is used below.

**Complete approval actually measured:** both screened and unscreened runs cost project show 1, task list 1, document list 1, guarded approval metadata write 2 = 5. The list supplies the document version to the existing authority; no extra approve ceremony is added. The capture records actual screening for create, priority update, approval and resolution.

Every retained tracker operation has a purpose: validate parent placement; resolve field/repository IDs once per manager; create; obtain board item ID through add; set the required fields in one aliased document; link to the existing project; set terminal status; close while recording state/reason. Metadata is written in create/update bodies, not separate metadata calls. No comments, board-wide scans, extra URL reads, extra priority-only prototype calls or post-create readback are retained. The actual create response supplies the canonical GitHub URL and Linear's actual create response supplies its canonical issue URL; assertions check them, and captures retain task ids/URLs. Existing CLI URLs are also checked. Conditional removal of 90 mapping reads would save 0.9/item, but is not a measured result or the target recommended here.

The model uses the plugin's worst_case_point_cost for every actual document: a batched mutation is one primary point here. Separately, every executed aliased mutation FIELD is counted, and conservatively charged five secondary points by the plugin pacing model. The 800 fields plus 110 reads total 4,110 secondary modeled points before recovery, 4,130 including the measured recovery probes. Do not confuse primary points, HTTP requests, aliased fields and secondary points. No live points were observed or spent; no fake client was priced.

Quota arithmetic: [GitHub's documented limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api) give a typical 5,000 primary points/hour and secondary constraints, including 2,000 GraphQL points/minute and generally 80 content-generating requests/minute, 500/hour. Ten managers share the credential; dividing gives 500 primary points/manager/hour. At 7.3/item that is about 68 tasks/manager/hour before other work, while the 100 creates alone consume 20% of the hourly content allowance. 4,110 secondary modeled points represent 2.055 minutes of sustained capacity; this is not measured latency or a scheduling guarantee. Global pacing must still govern simultaneous managers. Additional undisclosed limits can bind sooner.

Linear measured 1261 HTTP requests including its ten cold terminal retries; raw operations remain in linear.json.gz. Exploratory runs ranged 1,260–1,264 due to concurrent project-member pagination. It is not priced using GitHub's cost table: this plugin has no equivalent point model. [Linear's request and complexity limits](https://linear.app/developers/rate-limiting) distinguish API-key request capacity (2,500/hour, per user) from complexity. This run consumes about 50.44% of one hourly request allowance arithmetically; no live request/complexity quota was spent.

Exploratory and intentionally failing assertion probes were additional unaggregated local fixture traffic, not live consumption. The loopback disables hosted pacing/latency; these elapsed figures are not live throughput evidence.

Both new journeys were observed failing when terminal writes were intentionally skipped: GitHub observed OPEN instead of CLOSED; Linear observed todo instead of the terminal category. ## Design findings

- Required producer seam, not implemented: persist a plugin-owned durable intent under a lock keyed by source identity + external item_id BEFORE sending create; record phase, stable origin, payload digest, resolved route/project and eventually the returned task id/URL. A retry finding an existing binding reads/no-ops that ticket. A pending/ambiguous intent searches by the persisted origin and verifies item_id, route and payload before binding the one positive match; zero or multiple matches visibly refuse/reconcile, never issue a second create. Successful create carries the origin/item identity in its initial body, and its binding is durably recorded before acknowledging. Conflicting terminal state must refuse. Local claim and binding writes cost zero tracker requests, explicitly conditional on a plugin-owned durable store; the measured positive-origin recovery costs one tracker request/point. This is not an engine mirror or a consumer declaration change. Follow-up recorded links and origin searches alone are insufficient between create and binding, before board filing/index visibility, or with simultaneous uncoordinated owners. Multi-host claim arbitration and a permanently unindexed/orphan issue remain unproven and must visibly block rather than recreate. A remote claim design needing tracker writes must be remeasured before these targets are finalized.
- Operation-context seam: addSubIssue invalidates the existing full parent context, including a reusable repository placement mapping. Keeping only the validated parent id/repository mapping separately from mutable members/version would remove repeated routing reads without reusing stale approval authority. This was asked of the manager on correlation c-16157b00861732e403302d33c22ff51c; no reply arrived within its window. The report keeps all 90 reads and makes no lower measured claim. The earlier manager ruling c-c176a453b882a0f6a43da950295229ed explicitly permits conditional recommendations with a general claim/recovery producer seam; no target is finalized here.
- The warm prototype does not execute engine routing/privacy checks. Existing screened CLI calls and private/mixed refusal cases are measured separately. Proposed 7.3/13 targets therefore require the general producer to carry validated mapping/screening/version context without replaying the existing whole-project classification and comment readback for every task. A changed privacy/version precondition must revalidate or refuse; stale approval authority is never reused. Full future routing, malformed-v1 schema journeys, unknown socket-loss recovery and cross-host claims are not claimed implemented.
- Ordinary task create lacks a priority flag; the existing path must pay a separate update. An out-of-scope follow-up was recorded through ORCHESTRATOR_FOLLOW_UP_DRAFT. The prototype uses the existing ItemWrite priority and batches it with status/origin; no ordinary CLI feature was changed.
